# Conversation

Went in expecting to plan the fretboard viewer — the full-neck key/mode overlay felt like the obvious next thing to build, and the plan-mode research pass confirmed it was unblocked: both its foundation dependencies showed `status: done`. Before finalizing a plan, though, it seemed worth double-checking exactly how much that pass should bundle (bare correctness vs. also labeling vs. also a live switch UI), and whether the render surface's known octave-range gap should get fixed in the same breath.

That question turned out to be the wrong one to be asking. A quick check of the actual task files showed foundations wasn't done at all — two items, pentatonic subsets and the bounded region search, were still sitting at `status: todo`, contradicting the assumption they'd all wrapped up in an earlier session. Pivoted immediately: finish foundations properly before starting anything new on top of it.

The bounded region search had a clean, principled fix once the shape was clear: `nearest_occurrence` already guarantees its result sits within six semitones of the anchor in either direction, so the octave range needed to cover a fret window is exactly computable per degree, not a range that has to be guessed wide enough and hoped. Wrote `positions_in_window` around that, verified it against the existing (if accidental) reference implementation already sitting in the test file, and swapped it into the demo — same visual result, no more guessing.

Pentatonic came with a real design fork baked into its own done-when: whether the degree-subset mechanism it needed was the same one the future exercise-subsets recipe model would want. Reading that task's actual shape settled it — recipes there filter *positions* after projection (notes-per-string, fret ranges); pentatonic filters *degrees* before projection ever happens. Different layer, not the same mechanism. Built the narrow version — two presets, an unexported helper — and left the open "might these still share something someday" question for later instead of deciding it prematurely.

Mid-implementation (after the code was done and tests passing, right before visually confirming in the running app), the whole task-tracking system got scrapped for something better suited to how this actually works: a flat `worklog/` of finished-or-in-progress slices plus a `todo.md` backlog, replacing the `tasks/` folder's per-feature files and dependency graph. This entry is the first thing written in the new format — retroactively, since the code work itself predates the format existing.
