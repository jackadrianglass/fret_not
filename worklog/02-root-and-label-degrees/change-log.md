# Change log

- Added a `label_mode : Degree_number | Note_name` toggle ("Degrees\nNotes") to the control bar, threaded through state alongside the key controls.
- In-key dots now show a centered label: the scale-degree number or the literal note name, depending on the toggle — looked up via `Mode.degrees`/`Key.mode_root` matched against each position's concrete pitch class.
- Root notes (`degree = 1`) get a black outline halo around the filled dot in addition to the label.
- Bumped `position_dot_radius` from 8 to 11 so 1-2 character labels stay legible; off-key hollow rings are unaffected otherwise.
- The larger dot radius (plus the root halo) started covering the fret-number row under the lowest string. Fret-number y is now computed from `root_halo_radius` plus a fixed gap instead of a bare offset, so it stays clear of the dots regardless of radius.
- In-key dots no longer use a hardcoded red. They now read raygui's own selected/pressed style colors live (`Raygui.get_style (Control.Default \`Base_color_pressed/\`Border_color_pressed/\`Text_color_pressed)`, converted via `Raylib.get_color`) for fill, border, and label text — the same blue accent the toggle group and dropdown already show when an option is selected. Root halo stays black, unchanged.
- Reordered the control bar to read left-to-right as "C Major showing degrees": tonic dropdown, quality toggle, a "showing" label, then the degrees/notes toggle. Dropped the old "Key:"/"Show:" labels. The dropdown's `Raygui.dropdown_box` call stays last in the drawing code (so its expanded list still overlays correctly) even though it's now positioned leftmost on screen — draw order and screen position are independent.
- Converted the quality and label-mode `toggle_group`s to `dropdown_box`es, matching the tonic control. Each gets its own `_dropdown_open` bool in `state`, threaded with the same toggle-pulse XOR fix as the tonic dropdown. No overlap concerns between the three: their closed boxes and expanded lists all sit in distinct, non-overlapping x-ranges.
- Tightened the gap around the "showing" label — its rectangle and the dropdowns on either side had too much slack (a 50px gap before it). Shrunk the label's box and moved the label-mode dropdown in to close the gap.
- Control-bar widths were hand-picked pixel constants, independent of the actual text/font — would look wrong if the font size ever changed. Replaced with `dropdown_width`/`label_width`, which measure each control's own text (`Raylib.measure_text`) against raygui's live text size (`Control.Default \`Text_size`) and the dropdown arrow's reserved space (`Control.DropdownBox \`Arrow_padding`), then lay the four controls out left-to-right from a running x-cursor instead of separately hardcoded x positions.
- `dropdown_width`'s first cut sized the box to exactly where the centered text's edge meets the arrow's anchor point, with zero clearance — text visibly touched the arrow. Added `dropdown_text_to_arrow_gap` on top of the arrow's own reserved margin so there's a real gap between them.
- That fix widened the box, but raygui centers dropdown text by default — so the added width also opened up a matching, unwanted gap on the *left* (nothing sits there; only the right side has an arrow to clear). Set `DropdownBox` to left-align its text (`Raygui.set_style` in `setup`, once, globally) and switched `dropdown_width` to a small fixed left inset instead of mirroring the arrow's padding on both sides.
- Left-aligning wasn't enough on its own — `dropdown_left_text_padding` only budgeted the box's *width*, it didn't move where raygui actually starts drawing the text, so the text sat flush against the left border. raygui insets left-aligned text by its `TEXT_PADDING` style (0 by default), so the fix was to also set that style in `setup`, keeping the real inset and the width math driven by one shared value.
- That still had no visible effect: traced into raygui 2.2.2's C source and found `GuiDropdownBox` positions its text via `GetTextBounds(DEFAULT, bounds)`, not `GetTextBounds(DROPDOWNBOX, bounds)` — a control-id quirk in this raygui version. Setting `Text_padding` on `Control.DropdownBox` was silently ignored; switched to `Control.Default` instead, which is what the dropdown actually reads. `Label` draws via its own control id, so this doesn't affect the "showing" label. Documented the quirk in `contributing/raylib-raygui-reference.md` alongside the existing dropdown gotcha.
